# Phase 2 Architecture Review

## Summary
Phase 2 delivered the full persistence stack: a Postgres-16 docker-compose dev environment (`docker-compose.yml`), a Postgres-dialect `backend/db/schema.sql` covering all six entities with FK semantics, unit-normalization columns, and the `marketplace_link` bidirectional-uniqueness CHECK; a sqlc-generated data-access layer (`backend/internal/db/`) behind a `store.Querier` interface with a `WithTx` transaction seam; and a `go:embed`-based idempotent migration that auto-applies on startup. The phase goal — "design and instantiate the relational schema and data access layers" — is met cleanly, and the SQLite→Postgres pivot was executed without leaving stale SQLite config, deps, or comments behind. Verdict is **sound-with-concerns**: the foundation is solid and the `WithTx` seam is genuinely ready for Phase 3.3's atomic orchestrator (proven by `withtx_test.go`'s multi-step commit/rollback), but three things will bite Phase 3 immediately — (1) `main.go` still has no shared `*sql.DB` pool and no DI/wiring point, so the orchestrator has nowhere to receive a `store.Querier`; (2) the HTTP server timeouts from Phase 1 are unchanged and will cancel Vision LLM calls; (3) the schema/queries have no idempotent-ingestion support (no `UNIQUE` on `product.display_name`, no `UNIQUE` on `receipt.(correspondent_id, external_doc_id)`, no get-or-create / `ON CONFLICT` queries), which the Phase 3.3 "register new RawItems and Products if unseen" requirement depends on.

## Findings

### 1. No shared `*sql.DB` pool or DI wiring point in `main.go` [severity: risk]
**Observation:** `backend/cmd/server/main.go` calls `store.Migrate(cfg.DatabaseURL, dbembed.Schema)` (which opens and closes its own `*sql.DB` — `migrate.go:14`), then builds the chi router and registers the still-stateless `server.HealthHandler`. No `*sql.DB` is constructed for the app, no `*store.Store` is instantiated, and `server.Server`/`Handlers` struct from the Phase 1 arch review carry-over was never introduced. The `store.Store`/`store.New`/`store.Querier` types exist and are tested, but nothing in the running binary holds an instance.
**Impact:** This is the explicit Phase 3 carry-over flagged in PR #9's review ("instantiate a single `*sql.DB` pool + `*store.Store` after Migrate in main.go and inject `store.Querier` into the ingestion orchestrator"). Phase 3.3's orchestrator constructor wants `store.Querier`; Phase 4 handlers want it too. Without a wiring point, the first Phase 3 ticket either introduces globals or forces a mid-phase `main.go` + handler refactor. This is the single most important input to Phase 3 grooming.
**Recommendation:** First Phase 3 ticket (or a tiny Phase 2 follow-up before grooming): in `main.go`, after `Migrate`, open `sql.Open("pgx", cfg.DatabaseURL)` once with sane pool defaults (`SetMaxOpenConns`, `SetMaxIdleConns`, `SetConnMaxLifetime`), wrap as `store.New(db)`, introduce `server.Server{Querier: store.Querier, ...}` (or `Handlers` struct) with a constructor, and convert `HealthHandler` to a method as the first instance. Then Phase 3/4 handlers/orchestrators receive deps via the struct.

### 2. HTTP server timeouts unchanged — will cancel Phase 3 Vision LLM calls [severity: risk]
**Observation:** `main.go:51-58` still sets `ReadTimeout: 10s`, `WriteTimeout: 15s`, and the global `middleware.Timeout(30 * time.Second)` still wraps every route (`main.go:33`). PROJECT.md Phase 3.2 sends receipt image binaries to `https://ai.havek.es/api` and Phase 4.3 (`POST /api/receipts/upload`) runs that pipeline synchronously after a multipart read. Vision LLM calls on image input routinely run 10–60s.
**Impact:** Unchanged from the Phase 1 arch review (carry-over #1 and #3/#4). The first end-to-end Phase 3/4 run will fail with `context deadline exceeded` / write-reset that is hard to attribute. The global chi `middleware.Timeout` is also known to misbehave with large/streaming bodies.
**Recommendation:** Fold into the Phase 3 vision-LLM ticket (and the Phase 4 upload ticket): replace the global 30s chi timeout with per-route timeouts, raise or relax `http.Server` `ReadTimeout`/`WriteTimeout` for the upload route, and prefer the async pattern PROJECT.md already specifies for `/api/sync`. Do not carry these defaults into ingestion.

### 3. Schema/query layer has no idempotent-ingestion support [severity: concern]
**Observation:** The schema is faithful to the P2-T01 contract, but several constraints the Phase 3.3 orchestrator ("automatically register new RawItems and Products if unseen") needs are absent:
- `product.display_name` is **not UNIQUE** and there is **no `GetProductByName` query** (`db/queries/product.sql` only has `GetProduct` by id). The orchestrator's get-or-create-by-name pattern has no deterministic lookup; concurrent ingestion or re-runs will create duplicate `product` rows for the same canonical item.
- `receipt` has **no `UNIQUE(correspondent_id, external_doc_id)` where `source='paperless'`** — re-running the Paperless poll (Phase 3.1) risks duplicate receipts.
- `raw_item` has **no `UNIQUE(receipt_id, raw_text)`** — re-ingestion of the same receipt duplicates line items.
- `correspondent.name` is UNIQUE (good), but there is **no `GetCorrespondentByName` query** — the orchestrator needs get-or-create.
- No `ON CONFLICT DO NOTHING ... RETURNING` (upsert) queries anywhere; all creates are plain `INSERT ... RETURNING *`.

**Impact:** Phase 3.3 will immediately need to add: a `UNIQUE` constraint on `product.display_name` (or a deterministic normalization key), idempotent receipt/raw_item uniqueness, and get-or-create / `ON CONFLICT` queries. Because schema.sql is the documented "contract for Phase 3/4" (`backend/db/README.md` "Notes"), these additions are schema changes that should be coordinated, not silently slipped into an orchestrator ticket. The `marketplace_link` is also affected — its `CHECK(product_a_id < product_b_id)` means the orchestrator must sort IDs before insert (the queries don't help with this; `CreateMarketplaceLink` takes raw `product_a_id`/`product_b_id`).
**Recommendation:** Phase 3 grooming should include a "persistence gap" ticket (or fold into 3.3): add `UNIQUE` constraints for idempotent ingestion, add `GetXByName` queries for the get-or-create pattern, add `ON CONFLICT DO NOTHING/UPDATE ... RETURNING` upserts for `product`/`correspondent`/`receipt`, and document that the orchestrator must order `marketplace_link` IDs ascending before insert. Alternatively, decide deliberately that dedup is app-level and document why — but the missing lookups remain a gap either way.

### 4. `Migrate` existence-check is single-table and uses its own connection [severity: concern]
**Observation:** `backend/internal/store/migrate.go:26-34` checks only `information_schema.tables WHERE table_name = 'correspondent'` to decide whether to apply the schema. If the schema is partially applied (e.g. `correspondent` exists but `marketplace_link` does not — possible if a prior apply was interrupted or a later table was added to `schema.sql`), `Migrate` skips and leaves the DB in an inconsistent state. `Migrate` also opens its own `*sql.DB` (`migrate.go:14`) separate from the app pool, so the startup connection count is `1 (migrate) + N (app pool)` rather than reusing one.
**Impact:** Low probability today (greenfield, `CREATE TABLE IF NOT EXISTS` makes re-runs safe), but the single-table check is a false-positive risk as the schema evolves in Phase 3+. The separate connection is the carry-over already flagged in PR #9.
**Recommendation:** When the shared `*sql.DB` pool is introduced (Finding 1), refactor `Migrate` to accept a `*sql.DB` (or `DBTX`) so it reuses the pool. Optionally broaden the existence check to count expected tables or just always `ExecContext(schemaSQL)` and rely on `IF NOT EXISTS` (idempotent by construction) — simpler and removes the false-positive branch entirely. Fits inside the same wiring ticket.

### 5. Tests require a running Postgres — `go test ./...` is not hermetic [severity: debt]
**Observation:** `backend/internal/store/helpers_test.go` `testDB()` skips tests if `DATABASE_URL` is unreachable (`t.Skipf`), and `migrate_test.go` does the same. Every store test creates a throwaway schema (`test_<rand>`) via `search_path`, applies `schema.sql`, and drops it on cleanup — a clean, isolated pattern. But there is no in-memory / CI-without-Postgres path, and `migrate_test.go` hardcodes `localhost:5433` rather than reading `DATABASE_URL` (PR #9 nit, unfixed).
**Impact:** A reviewer/CI without `docker compose up -d` gets silently-skipped store tests — false green. The hardcoded `localhost:5433` in `migrate_test.go` breaks against any non-default Postgres. The pattern itself (throwaway schema per test) is excellent and should be the convention.
**Recommendation:** Phase 3 grooming nit: make `migrate_test.go` reuse the env-aware `testDB`/`DATABASE_URL` helper (or read `os.Getenv("DATABASE_URL")` with the same default) for consistency. Optionally add a CI step that fails the build if store tests are *skipped* (not just failed) so silent skips surface. No standalone ticket — fold into the next store-touching ticket.

### 6. Two packages named `db`; doc drift persists [severity: debt]
**Observation:** `backend/db/` (the `go:embed` package) and `backend/internal/db/` (sqlc-generated) are both package `db`. `main.go` imports the embed one as `dbembed` (`main.go:18`); tests in `store` import both unaliased (`helpers_test.go:18` vs `withtx_test.go:14` `internal/db`). The root `README.md` still reads `frontend/  # SvelteKit web app (coming in Phase 1)` (Phase 1 arch review grooming nit, still open). `config_test.go` was requested in the Phase 1 arch review and is still absent (`backend/internal/config/` contains only `config.go`).
**Impact:** Low-interest. The two-`db`-package situation is mildly confusing but `go` handles it; the README line and missing config test are cosmetic/coverage debt that won't compound.
**Recommendation:** No standalone ticket. When the wiring ticket (Finding 1) touches `main.go`/imports, consider renaming the embed package to `dbembed` (or `dbschema`) to drop the alias. Update root `README.md` structure block and add `config_test.go` (defaults + env overrides) the next time a doc/test ticket is open.

## What went well
- **The SQLite→Postgres pivot was executed cleanly.** No SQLite leftovers: `DB_PATH` gone from `config.go` and `.env.example`; `go.mod` carries only `pgx/v5` (no `modernc.org/sqlite`); `.gitignore` has no `*.db`/`data/` cruft; `backend/db/README.md` SQLite PRAGMA section removed and replaced with the docker-compose dev section; schema converted to Postgres dialect (`BIGINT GENERATED ALWAYS AS IDENTITY`, `DOUBLE PRECISION`, `TIMESTAMPTZ`, named CHECK constraints, `COMMENT ON`). This simultaneously resolved Phase 1 arch review carry-over #3 (the `.gitignore`/`DB_PATH` concern) — Postgres data lives in a docker named volume, never in the repo tree.
- **Schema fidelity to the downstream contract is high.** All six tables, all FK `ON DELETE` semantics (RESTRICT/CASCADE/SET NULL chosen deliberately and documented in the README's FK table), the `marketplace_link` bidirectional uniqueness via `UNIQUE(product_a_id, product_b_id)` + `CHECK(product_a_id < product_b_id)` (also disallows self-links, documented), and the full unit-normalization column set (`raw_item.raw_quantity`/`quantity_value`/`quantity_unit`, `product.base_unit`, `price_record.unit_price`) all match the P2-T01 design that Phase 3/4 will consume. Table/column names are identical to the cancelled ticket's contract — the pivot changed dialect, not names.
- **The `WithTx` seam is genuinely ready for Phase 3.3.** `store.Store.WithTx` shadows the sqlc `Queries.WithTx` to return the `store.Querier` interface, so the orchestrator can do `txQ := q.WithTx(tx); txQ.CreateCorrespondent(...); txQ.CreateReceipt(...); txQ.CreateRawItem(...); txQ.CreatePriceRecord(...); tx.Commit()` all in one transaction. `withtx_test.go`'s "multi-step atomic write" subtest exercises exactly this shape (correspondent→receipt→raw_item→price_record) and proves commit/rollback semantics. A compile-time check (`var _ Querier = (*Store)(nil)`) guards the interface.
- **sqlc config is correct for the Postgres pivot.** `sqlc.yaml` uses `engine: "postgresql"`, `sql_package: "database/sql"` (so it slots onto the stdlib `*sql.DB`/`*sql.Tx` that `pgx/v5/stdlib` registers), `emit_interface: true` (generates `db.Querier`), `emit_exact_table_names: false` (clean Go names: `Correspondent`, `MarketplaceLink`), `emit_empty_slices: true` (no nil-slice surprises for API handlers). `sqlc generate` is reproducible (v1.31.1, noted in generated headers).
- **Throwaway-Postgres test pattern is well-factored and should be the convention.** `helpers_test.go`'s `testDB(t)` creates a random `test_<8char>` schema, sets `search_path`, applies the embedded `schema.sql`, and registers a cleanup that `DROP SCHEMA CASCADE`s — tests are isolated, parallel-safe, and leave no state. `migrate_test.go` separately validates *both* the idempotent-skip branch and the apply-on-empty branch (the latter via a throwaway *database*, addressing PR #9 cycle-1 finding #2).
- **Every Phase 2 PR-review carry-over was addressed, not silently dropped.** Port consistency fixed across `.env.example`/`config.go`/`docker-compose.yml`/both READMEs (all `5433`); `TestMigrateAppliesSchemaOnEmptyTarget` added to cover the apply branch; typos fixed ("Embeds", "CHECK"); gofmt fix applied. Non-blocking nits were explicitly carried forward (shared pool → Finding 1 here; hardcoded test port → Finding 5 here) rather than dropped.
